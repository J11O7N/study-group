# study-group
# 오픈 미션 - 스터디그룹

---
## 🎯 목표
```text
프리코스에서 제가 가장 인상 깊게 느꼈던 경험은 스터디에 참여했던 순간들이었습니다.
그때의 기억들은 함께 성장하고 배우며 느꼈던 성취감과 즐거움으로 오래 남았습니다.
그래서 이 경험을 직접 하나의 스토리로 풀어내고, 제가 배운 프로그래밍 기술로 재구성해 보고자 했습니다.
그 결과, 스터디 운영의 전 과정을 하나의 흐름으로 표현한 ‘스터디그룹’ 오픈미션을 만들게 되었습니다.

```

## 기능 목록
### 1. 입력

| 항목        | 설명                                                                                   |
| --------- | ------------------------------------------------------------------------------------ |
| 팀장 정보 입력  | 이름, 분야, 가능 지역, 가능한 요일·시간, 선정 키워드 3개                                                  |
| 지원자 정보 입력 | 이름은 `com.github.javafaker.Faker(ko)`로 랜덤, 분야/사는 지역/가능 시간은 프로젝트 내 직접 정의 리스트에서 랜덤 선택 + 지원동기|
| 입력 형식     | CLI 입력                                                                  |
| 검증 로직     | 공백, 중복 이름 허용, 유효하지 않은 시간대/없는 지역/없는 분야 차단, 키워드 최소 1개 이상                               |

---

### 2. 필터링 및 선발

| 항목 | 설명                                |
| -- | --------------------------------- |
| 분야/지역 필터링 | 리더 기준으로 사전 필터링    |
| 시간 필터링 | `TimeMask`(7×24 비트마스크) 기반 교집합 도출 |
| 선정 정책(최종) | 팀장이 지정한 키워드가 지원동기에 1개 이상 포함된 지원자만 최종 후보 |
| 정원 | 정원 초과 시 선착순(등록 순서) 로 컷. |
| 최대 인원 | 팀장 포함 최대 5명(설정값으로 변경 가능)          |

| 항목       | 설명                                          |

# 1️⃣ Record 기반 도메인 구조 설계

- 모든 필드는 자동적으로 final → 불변 보장
- 불변 모델 기반이라 도메인 안정성 확보
- getter 대신 field 이름 그대로 사용 → 가독성 증가
- SelectionResult, Applicant, Leader 등 핵심 도메인에 모두 적용

---

# 2️⃣ Stream 기반 4단계 필터링 로직

스터디 그룹 매칭에는 다음 규칙이 적용된다:

```
1. 분야 일치 (Field)
2. 지역 포함 (Region)
3. 공통 가능한 시간 존재(TimeMask)
4. 키워드 포함(Motivation)
```

초기에는 if 문과 List 반복문으로 구성했으나 다음 문제가 발생했다.

### ■ 초기 구조의 문제

- 조건이 늘어날수록 코드가 수직으로 길어짐
- 필터링 순서 바꾸거나 제거할 때 사이드 이펙트 발생
- 가독성이 크게 떨어짐

# 4️⃣ TimeMask 설계 및 파싱 이슈

시간 입력 `"월13-16,화10-12"` 같은 문자열을
Day + TimeRange + boolean[7][24] 형태의 TimeMask로 변환.

### 주요 고민들

- 시간 파싱 로직이 15라인 넘지 않도록 분리 필요
- `"수14-16"`에서 day 파싱 시 substring(0,1) 가능?
- `'14-16'`을 어떻게 범위로 변환?
- 잘못된 구간(`20-3`) 처리 어떻게 해야 하는지?

### 해결 과정

- TimeMaskParser.parse()에서 String.split(",") 사용
- `TimeRange` record 내부에서 유효성 검사 구현

# 5️⃣ 장소 추천 설계 과정

### 출발점

- 리더 + 팀원들의 지역을 기반으로 가장 중심 지역을 찾고
- 그 지역과 가장 가까운 스터디 카페를 추천

### 고민했던 이슈들

- "홍대·강남·강남" → 중심이 어디인가?
- 최적화 기준은 "최소 거리 합"인가 "최소 최대 거리"인가?
- distance table에 없는 지역은 어떻게 처리?
- 후보가 0개일 때는?

### 최종 알고리즘

```
각 지역 = 후보
각 후보 지역에서 팀원 전체까지의 거리 합을 계산
거리 합이 가장 작은 지역 = 중심 지역
→ 중심에서 가장 가까운 카페 = 추천
```

### 발생했던 문제

- 신촌에 사는 사람이 없는데 왜 신촌점이 추천이되는가 ?
  → 중심이 신촌에 가장 가깝기 때문 (순수 거리합 기준)
